# Usage Guide


## 1. What it does

Your `Settings` class is the single source of truth. `pydantic-env-manager` keeps two files consistent with it:

| File | What happens |
|---|---|
| `.env.example` | Regenerated from `Settings` every time. Annotated with type, default and required-ness. Never contains secrets. |
| `.env` | Merged, never overwritten. Missing keys are appended; your values, comments and order are kept; nothing is deleted. |

## 2. Install

```bash
pip install pydantic-env-manager
```

Requires Python ≥ 3.9 and `pydantic-settings` ≥ 2 (installed automatically).

## 3. Example settings

```python
# app/settings.py
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="APP_", env_file=".env")

    port: int = Field(8000, description="HTTP port")
    debug: bool = False
    api_key: SecretStr  # required, no default
```

## 4. CLI

```bash
pydantic-env-manager sync  app.settings:Settings    # write .env.example, merge missing keys into .env
pydantic-env-manager check app.settings:Settings    # write nothing; exit 1 if files have drifted
```

The target is an import path, `module:Class`. It is resolved from the current directory.

| Option | Default |
|---|---|
| `--env PATH` | The class's `env_file` setting, else `.env` |
| `--example PATH` | `.env.example` in the same folder as the env file |

### What `sync` produces

`.env.example` (fully generated):
```
# Generated by pydantic-env-manager from app.settings.Settings. Do not edit by hand.

# APP_PORT (int, default: 8000) - HTTP port
APP_PORT=8000

# APP_DEBUG (bool, default: false)
APP_DEBUG=false

# APP_API_KEY (SecretStr, secret, required)
APP_API_KEY=
```

`.env`, starting from `APP_PORT=9000` and `LEGACY=1`:
```
APP_PORT=9000

# REQUIRED
APP_API_KEY=
APP_DEBUG=false

# Your additional env variables
LEGACY=1
```

### What `check` does

Exits `1` when `.env.example` is out of date or `.env` is missing keys. Extra keys in `.env` are printed as notes and never fail the check. If `.env` doesn't exist the `.env` check is skipped, so it works in CI.

Use it in CI:
```bash
pydantic-env-manager check app.settings:Settings
```

Or as a git pre-commit hook (`.git/hooks/pre-commit`, mark executable):
```bash
#!/bin/sh
pydantic-env-manager check app.settings:Settings
```

## 5. Python API

```python
from pydantic_env_manager import sync_env, check_env

result = sync_env(Settings)                       # SyncResult(example_changed, env_changed)
report = check_env(Settings)                      # CheckReport(problems, notes, missing); .missing lists keys absent from .env
sync_env(Settings, env_file="cfg/.env", example_file="cfg/.env.example")
```

## 6. Sync on app boot (local dev)

Subclass `EnvManagedSettings` and set `env_sync_on_init = True`. Both files sync whenever the settings object is created.

```python
from pydantic_env_manager import EnvManagedSettings

class Settings(EnvManagedSettings):
    env_sync_on_init = True
    port: int = 8000

settings = Settings()   # .env and .env.example are now in sync
```

Safety behaviour:
- Off unless `env_sync_on_init = True`.
- Skipped when the `CI` or `PROD` environment variable is set (anything except empty, `0` or `false`).
- If writing fails (read-only filesystem, permissions), it logs a warning and the app still starts.

## 7. Rules worth knowing

- **Your `.env` is safe.** Existing keys keep their values, inline comments and order. Nothing is removed or overwritten. A brand-new `.env` is created with owner-only permissions.
- **Secrets are never written.** `SecretStr` / `SecretBytes` fields are blank in both files, even if they have a default.
- **Running it twice changes nothing.** Unchanged files are not rewritten.
- **Key names.** `env_prefix` + field name, uppercased unless `case_sensitive=True`. A field with a `validation_alias` uses the alias as-is, because `pydantic-settings` does not apply the prefix to aliased fields. For `AliasChoices` the first choice is used; `AliasPath` fields are skipped with a warning.
- **Required fields** are written blank. Blank is not a missing value to Pydantic: a required `str` loads as an empty string, while a required `int` or `bool` fails validation.
- **Settings constants:** annotate with `ClassVar` (e.g. `MAX_RETRIES: ClassVar[int] = 3`). Pydantic does not treat them as fields, so they are never read from env nor written to either file. Every other annotated field is an env var.
- **Multi-line quoted values** and `export KEY=...` lines in `.env` are preserved.

## 8. Using it with AI coding agents

Block your agent from reading `.env` (for example with its ignore or deny settings) and point it at `.env.example`. That file is regenerated from code, so it is current, and it lists every variable with its type, default and whether it is required, without any secret values.

## 9. Not supported in v1

Nested models (`env_nested_delimiter`), multiple Settings classes, yaml/toml/secrets-dir sources, and `.env.test` / `.env.prod` variants.
